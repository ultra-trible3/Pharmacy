MASTER PROJECT PROMPT — PROFESSIONAL PHARMACY MANAGEMENT & POS SYSTEM
1. Your Role

Act as a Principal Software Architect, Senior Full-Stack TypeScript Engineer, Electron Desktop Engineer, Database Architect, QA Engineer, and UI/UX Designer.

Your mission is to design, implement, test, and document a production-oriented Pharmacy Management and Point of Sale (POS) desktop application.

Do not build only a demo, static UI, landing page, or collection of disconnected CRUD screens.

Build a coherent, functional application with real database persistence, business logic, validation, error handling, hardware integration adapters, automated tests, and deployment documentation.

Work incrementally. Inspect the existing repository first, create an implementation plan, and then implement the application in small, verifiable phases.

Do not claim a feature is complete unless its implementation and relevant tests exist. Never fake hardware access, successful printing, barcode scanning, database persistence, or completed sales.

2. Business Context

The application manages one pharmacy business with:

One or more checkout terminals.
One central server and shared PostgreSQL database.
A local area network (LAN).
Offline operation without an internet connection after installation.
Arabic-first RTL user interface, with optional English localization.
Egyptian pharmacy workflows, configurable EGP currency, and local date/time settings.
Support for barcode scanners, thermal receipt printers, cash drawers, and A4 printers.
Reliable inventory tracking by product batch, lot number, and expiration date.

The architecture must support multiple cashiers using the same database concurrently.

The server is the authoritative source for sales, stock quantities, pricing rules, permissions, and financial transactions.

Do not make cloud access or an external API mandatory for ordinary local sales.

4. Architecture

Organize the repository into clearly separated applications and shared packages.

Suggested structure:

apps/ desktop/ src/ main/ preload/ renderer/ app/ components/ features/ layouts/ pages/ hooks/ lib/ i18n/ tests/ server/ src/ auth/ users/ roles/ products/ categories/ manufacturers/ suppliers/ customers/ inventory/ batches/ purchasing/ sales/ returns/ payments/ cash-register/ expenses/ reports/ barcode/ printing/ audit/ backup/ settings/ health/ prisma/ test/

packages/ shared-types/ validation/ eslint-config/ tsconfig/

docs/ architecture.md database-schema.md hardware-setup.md installation.md backup-and-restore.md user-manual.md security.md implementation-status.md

Use a modular monolith for the backend. Avoid microservices unless a demonstrated requirement justifies them.

Separate domain logic, application services, persistence, API controllers, and infrastructure adapters.

Keep the Electron renderer isolated from privileged operating-system APIs. Enable context isolation and sandboxing, disable Node integration in the renderer, and expose only narrowly scoped, validated IPC methods through preload.

Never expose unrestricted filesystem, shell, process, or Node.js APIs to the renderer.

5. Authentication and Authorization

Implement:

Role-based access control.
Roles such as Owner, Manager, Pharmacist, Cashier, Inventory Clerk, and Accountant.
Fine-grained permissions for viewing, creating, editing, deleting, refunding, discounting, adjusting inventory, opening the cash drawer, viewing costs, and accessing reports.
Session expiration and revocation.
Failed-login throttling and appropriate audit records.
PIN-based cashier workflows only if implemented securely.
Server-side authorization for every protected operation.

The frontend may hide unauthorized actions, but backend enforcement is mandatory.

Never store plaintext passwords or privileged database credentials in renderer code.

9. Point of Sale (POS)

Build a fast, keyboard-friendly checkout screen.

Required capabilities:

Scan barcode and add the matching product to the cart.
Search products by Arabic/English name, SKU, or barcode.
Support multiple items in a single sale.
Edit quantities, remove items, and apply authorized discounts.
Show available stock and applicable batch/expiry information.
Calculate line totals, invoice totals, discounts, taxes where applicable, and change due.
Support configurable payment methods: cash, card, and other locally available methods.
Support split payments when appropriate.
Handle suspended and resumed carts.
Hold and retrieve pending sales.
Handle returns and refunds according to permissions.
Print and reprint receipts with audit logging.
Support configurable receipt templates and Arabic RTL printing.
Provide clear loading, success, validation, and failure states.
Protect against accidental double submission.
Preserve a recoverable checkout state after a temporary network interruption, without falsely marking a sale as completed.

The backend must revalidate prices, permissions, discounts, and stock at checkout time.

The final sale must be processed atomically. A sale must not be partially saved.

Use database transactions, appropriate locking or conditional updates, and idempotency keys to prevent duplicate invoices and overselling during concurrent checkout.

Assign unique invoice numbers safely under concurrent usage.

Document the exact behavior when payment authorization, stock deduction, invoice persistence, or printing fails.

Printing failure after a committed sale must not create a duplicate sale when the cashier retries printing.

14. Hardware Integration

Create explicit hardware adapter interfaces and separate them from business logic.

A. Barcode scanners:

Support common USB HID keyboard-wedge scanners.
Detect scan completion using configurable suffixes or timing.
Avoid treating ordinary typing as a scan without suitable detection rules.
Support real scanner testing and a manual-entry fallback.

B. Receipt printers:

Support compatible thermal printers.
Prefer documented ESC/POS-compatible adapters where appropriate.
Support USB, shared Windows printers, and network printers according to the chosen implementation.
Support Arabic RTL receipts, configurable paper width, logo, invoice number, totals, payment details, and QR/barcode elements when needed.
Include test-print and connection-status workflows.

C. Cash drawers:

Support drawers connected through a compatible receipt printer's drawer-kick interface or another explicitly supported interface.
Open only after an authorized, policy-compliant action.
Default to opening after a successful cash sale where configured.
Require explicit permissions for manual opening.
Audit manual drawer-opening actions.
Never report successful physical opening unless the hardware or driver provides a reliable acknowledgment. Many drawers have no sensor confirming their state.

D. A4 printers:

Support Windows-installed printers and appropriate print-dialog workflows.
Print reports, purchase documents, stock counts, and other supported documents.

E. Device management:

Create a hardware settings page.
Configure printer selection, paper width, receipt copies, barcode settings, and drawer behavior.
Provide diagnostic and test-print buttons.
Log errors without exposing secrets.
Use mocks for development and tests.
Clearly label simulated devices as simulations.
Document real-device compatibility and limitations.

Use Electron's secure IPC or suitable Node.js hardware adapters. Do not attempt to access arbitrary device paths from the renderer.

20. Database and Data Integrity

Design a normalized PostgreSQL schema with proper foreign keys, constraints, indexes, and timestamps.

Use appropriate monetary precision such as PostgreSQL NUMERIC and a consistent application representation. Never rely on floating-point arithmetic for financial calculations.

Use database transactions for:

Sales and sale items.
Stock deductions.
Purchase receiving.
Returns and refunds.
Cash movements.
Inventory adjustments.

Use optimistic or pessimistic concurrency controls as appropriate.

Preserve immutable historical transaction details, including the product name, price, quantity, and cost basis needed to reproduce past invoices and reports.

Use soft deletion or archival for master data where appropriate. Never cascade-delete completed financial transactions.

Provide migrations and a documented seed process. Seed accounts must be development-only or require secure initial setup; never ship a well-known default production password.

List files and modules created.
Report tests and commands actually run.
Identify incomplete functionality and known limitations.
Update docs/implementation-status.md.
Continue to the next phase when safe and feasible.

Do not stop after generating a plan if implementation can proceed. If the task is too large for one iteration, complete a working vertical slice first and continue incrementally.
